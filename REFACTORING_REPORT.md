# Звіт з аудиту та плану рефакторингу

**Проєкт:** UA Air Alerts — застосунок Flutter для моніторингу повітряних тривог в Україні  
**Дата аудиту:** 10 жовтня 2026 року  
**Статус:** лише аналіз і рекомендації. Жодна рекомендація нижче не імплементована.

## 1. Короткий висновок

Проєкт уже має робочу основу Flutter-застосунку: функціональність зібрана в `features/alerts`, є DTO та мапер даних, Cubit для стану екранів, `go_router`, локалізація українською й англійською, фонова перевірка та окремі сервіси. Повний рефакторинг доцільно робити не як переписування всього з нуля, а як послідовне посилення наявної структури: спершу стабілізувати конфігурацію та API/стани, потім відокремити доменну логіку й інфраструктурні залежності від UI, далі додати тести, а вже після цього полірувати платформні збірки й UX.

Найважливіші підтверджені проблеми:

1. `flutter test` зараз **падає**, бо єдиний тест перевіряє застарілий лічильник із шаблону Flutter, якого в застосунку немає.
2. Трактування статусу тривоги через `contains('A')` дублюється в UI-кубіті та фонового сервісі; це не точний парсер API-статусу.
3. Запуск залежить від `.env`, а помилка його відсутності не обробляється до `runApp`; водночас README називає токен «secure», хоча значення потрапляє у `SharedPreferences` і клієнтський бінарник.
4. `RegionAlertsCubit` поєднує стан UI, сховище налаштувань, геолокацію, зіставлення області та керування фоновою задачею.
5. Дозволи запитуються до першого показу UI; у потоці геолокації після запиту дозволу залишається перевірка попереднього значення.
6. Немає змістовного автоматизованого покриття та CI-перевірок; статичний аналіз проходить, але це не виявляє описану логічну помилку тесту.

## 2. Межі аудиту та перевірки

Переглянуто структуру `lib/`, основні модулі API та фонової роботи, конфігурацію залежностей, README, налаштування аналізатора, тест і Android release-конфігурацію.

Виконані команди:

- `flutter analyze` — **успішно**, повідомлень про проблеми немає.
- `flutter test` — **неуспішно**: `test/widget_test.dart:19` очікує текст `0`, але віджет його не містить; падає тест `Counter increments smoke test`.

У робочому дереві до початку аудиту були вже змінені `pubspec.yaml` та згенеровані plugin registrant-файли для Linux/macOS/Windows. Цей звіт їх не змінює. Перед майбутніми змінами залежностей варто окремо з’ясувати, які саме з цих змін є навмисними.

## 3. Поточна структура та що вже зроблено добре

- Точка запуску й конфігурація застосунку зосереджені в `lib/main.dart`.
- Основний функціонал згрупований у `lib/features/alerts/`; data та presentation уже розділені на підпапки.
- API-модель, згенерований JSON-парсер і мапер розділені: `data/dto/`, `data/entity/`, `data/mapper/`.
- Навігація винесена в `lib/router/app_router.dart`; екрани переходять за іменованими маршрутами.
- Для стану використовується BLoC/Cubit із явними станами завантаження/успіху/помилки.
- Є українська й англійська локалізації, тема винесена окремо.
- Репозиторій приймає `CacheManager`, а Cubit-и приймають репозиторій через конструктор — це дає початкову можливість для ін’єкції залежностей і тестування.

## 4. Виявлені проблеми та рекомендації

### 4.1. Тестова база та якість перевірок — критичний пріоритет

**Факт:** `test/widget_test.dart` — незмінений шаблонний тест лічильника. Він перевіряє `0`, кнопку `Icons.add` і значення `1`, хоча застосунок відстежує тривоги. Фактично тест падає на першій перевірці. Інших тестів у `test/` не виявлено.

**Рекомендація:** замінити шаблонний тест набором тестів, що відповідають продукту:

- unit-тести DTO/мапера й обробки коректних та некоректних payload;
- тести репозиторію з підмінним HTTP/cache-рівнем: статус-коди, таймаути, помилкова JSON-схема, порожній/невалідний токен, примусове оновлення;
- тести Cubit-ів для loading/success/error, вибору регіону, відновлення стану та зміни тривоги;
- widget-тести для станів карти/регіону, повторної спроби та повідомлень про дозволи;
- ізольовані тести мапінгу регіонів і логіки фонового повідомлення.

Необхідно також додати CI, який при кожному PR запускає `dart format --set-exit-if-changed`, `flutter analyze`, `flutter test` і визначені для релізу platform build-перевірки.

### 4.2. Нечітке декодування статусу тривоги — високий пріоритет

**Факт:** `RegionAlertsCubit` і `background_alert_service.dart` окремо визначають активний стан через пошук символу/підрядка `'A'`. Це може помилково трактувати неочікувану відповідь або формат, а дві реалізації з часом можуть розійтися.

**Рекомендація:** перевірити офіційний формат відповідей alerts.in.ua й реалізувати один типізований парсер (наприклад, enum/результат active/inactive/unknown). Повторно використовувати його у foreground та background flow. Невідому відповідь показувати/логувати як контрольовану помилку, а не як активну чи неактивну тривогу.

### 4.3. Розподіл відповідальностей і залежностей — високий пріоритет

**Факт:** екрани самостійно створюють `AlertsRepository`; Cubit залежить від конкретної data-реалізації та `ApiError`. `RegionAlertsCubit` також виконує читання/запис `SharedPreferences`, виклик геолокації/geocoding, зіставлення назви області, виклик фонового сервісу та керування UI-станом.

**Рекомендація:** додати єдину composition root / app-level providers для створення залежностей. Ввести абстракції для роботи з alerts API та збереженими налаштуваннями. Розділити логіку геолокації й фонової роботи на сервіси, а правила визначення активного статусу та вибору області — на тестовану доменну логіку. Не обов’язково відразу створювати багато шарів/use-case класів: спочатку провести чіткі межі навколо зовнішніх ефектів і бізнес-правил.

### 4.4. Конфігурація API та поводження з ключами — високий пріоритет

**Факт:** `main()` безумовно завантажує dotenv до `runApp`; збій завантаження може перервати запуск. Токен `API_TOKEN` передається через `SharedPreferences` фоновому сервісу. Це звичайне сховище налаштувань, не сховище секретів. Значення, вбудоване у Flutter-клієнт, не можна вважати конфіденційним. README помилково описує `flutter_dotenv` як «secure token management».

**Рекомендація:** створити чіткий config-рівень із валідацією обов’язкових/необов’язкових параметрів, безпечним запуском без необов’язкової конфігурації та зрозумілою помилкою для користувача/розробника, якщо API недоступне через відсутній токен. Не копіювати приватні облікові дані в `SharedPreferences`. Якщо ключ має бути справді секретним, потрібен серверний посередник; якщо API постачальника розраховане на клієнтський токен, його треба вважати видимим, обмежувати квотами й мати план ротації.

`API_TOKEN` для alerts.in.ua — це не те саме, що API-key картографічного провайдера. Наявна карта побудована зі статичних локальних зображень, тому зараз map-provider key у коді не використовується й не потрібен.

#### Точне майбутнє місце для публічного ключа карти

Якщо після вибору картографічного SDK провайдер вимагатиме ключ, рекомендоване місце конфігурації — **`lib/core/config/app_config.dart`**, у полі з назвою на кшталт `mapPublicApiKey`. У цей файл слід додати лише читання compile-time параметра, наприклад `String.fromEnvironment('MAP_PUBLIC_API_KEY')`, а фактичне значення передавати під час запуску/збірки через `--dart-define=MAP_PUBLIC_API_KEY=...` або CI secret. Так значення не потрапить у Git. Воно все одно буде доступне зібраному клієнту, отже його потрібно вважати **публічним**, обмежити за ідентифікатором застосунку/підписом/доменом та квотами у провайдера. Не зберігати цей ключ у `SharedPreferences` і не плутати його з `API_TOKEN` alerts.in.ua.

**Отже, зараз ключ нікуди додавати не потрібно.** Точний рекомендований файл після погодженого рефакторингу: `lib/core/config/app_config.dart`; реальне значення передавати на етапі build/run, а не комітити у файл. Якщо надалі буде вимога саме локального файлу для розробки, його потрібно окремо ігнорувати в Git та не пакувати як нібито секрет у production.

### 4.5. API transport, кеш та обробка помилок — високий пріоритет

**Факт:** репозиторій самостійно отримує файл із `CacheManager`, читає його, декодує JSON і трактує частину помилок API. Не нормалізовано окремо мережеві/HTTP-помилки, статус-коди та різні форми error payload. Cubit-и для неочікуваних винятків можуть віддавати `e.toString()` UI. Модель і мапер покладаються на обов’язкові поля й прямий `DateTime.parse`.

**Рекомендація:** винести transport-клієнт із timeout, валідацією HTTP status/content і контрольованою політикою кешу. Парсер має повертати узгоджені типізовані помилки; UI має відображати локалізовані повідомлення без технічного stack/error text. Додати тести на відсутні поля, неправильні типи, невалідну дату, помилкову відповідь та невідомі значення. Для кешу явно визначити TTL, stale data policy та поведінку при offline.

### 4.6. Ініціалізація застосунку й дозволи — високий пріоритет

**Факт:** до `runApp` виконуються dotenv, preferences, background initialization/registration та запит дозволів. Це затримує перший кадр і просить дозволи до того, як користувач побачив відповідну можливість. Помилки bootstrap/config не мають окремого користувацького відновлення.

**Рекомендація:** залишити до першого кадру лише необхідну ініціалізацію. Решту оформити як контрольований bootstrap з екраном/станом помилки або відкласти до функції, що потребує дозволу. Запит location/notifications робити контекстно, пояснивши призначення; обробляти denied, denied forever, вимкнений системний сервіс і повернення з налаштувань.

### 4.7. Геолокація й зіставлення регіонів — середньо-високий пріоритет

**Факт:** після `requestPermission()` частина розгалужень перевіряє попереднє значення дозволу; зіставлення області базується на тексті назви та локальному списку варіантів. Результат може бути крихким до локалі/формату geocoding-провайдера.

**Рекомендація:** використовувати тільки актуальне значення дозволу після кожного кроку; ізолювати permission flow. Перевагу надавати стабільним ідентифікаторам/нормалізованій таблиці відповідностей, а не довільному substring у назві. Додати тести українських/англійських назв, відмінків, альтернативних назв та невідомих результатів.

### 4.8. Надійність фонових сповіщень — середньо-високий пріоритет

**Факт:** помилки реєстрації та виконання фонового сервісу переважно поглинаються; UI не показує, чи моніторинг реально запущено. Періодичний інтервал WorkManager є best-effort і не гарантує точного виконання кожні п’ять хвилин. Виклики start/stop з Cubit не очікуються асинхронно.

**Рекомендація:** повертати й зберігати стан реєстрації моніторингу, обробляти відмову/помилку в UI, очікувати async-операції та логувати діагностику без токенів і персональних даних. Розрізняти тимчасову мережеву помилку й некоректну конфігурацію. Документувати обмеження OS scheduler і не обіцяти точну частоту тривог у фоні.

### 4.9. UX, локалізація, доступність і продуктивність — середній пріоритет

- На екрані карти дата відображається у фіксованому англомовному форматі, попри підтримку двох мов.
- Список будується eager-підходом; доцільно перевірити lazy rendering на великих відповідях.
- Поверх статичного зображення України компонуються локальні растрові області. Виміряти розмір assets та час перемальовування на цільових пристроях перед оптимізацією.
- Для карти й індикаторів статусу потрібні семантичні описи, а для icon-only кнопок — доступні назви. Перевірити великі шрифти, контраст, screen reader і reduced motion.
- `LocaleCubit` має початкову українську локаль і не зберігає вибір користувача після перезапуску.
- Відображення стану збереженого регіону/вибору частково читається напряму з Cubit замість повного immutable state, що може ускладнювати повторне відображення й тестування.

### 4.10. Платформна готовність і документація — середній пріоритет

**Факт:** залежності охоплюють геолокацію, фон, сповіщення та аудіо, але потребують різної підтримки/налаштування за платформами. Android release-конфігурація зберігає шаблонний `com.example` application ID і debug signing. README описує карту як інтерактивну, хоча зараз це локальне статичне зображення з overlay областей; документ також називає dotenv керуванням секретами й не пояснює обмеження фону/дозволів.

**Рекомендація:** визначити офіційно підтримувані target-платформи й можливості на кожній. Для Android перед релізом встановити production application ID і release signing через захищене CI/local secret-сховище. Для непідтримуваних платформ показувати контрольовану недоступність фонової роботи замість тихого збою. Оновити README під фактичну реалізацію, налаштування ключів, дозвільний UX, offline поведінку, тестові команди та платформні обмеження.

## 5. Пропонований план робіт (на погодження)

### Етап 0 — зафіксувати вихідний стан

- Визначити, які попередні зміни в `pubspec.yaml`/registrant-файлах залишаються в роботі.
- Визначити підтримувані платформи та бажаний тип карти: локальні assets чи зовнішній картографічний SDK.
- Зафіксувати контракт API alerts.in.ua для статусів, кодів помилок і кешування.

### Етап 1 — надійний запуск та API boundary

- Зробити bootstrap/config перевіреним і відновлюваним.
- Визначити правильне поводження з API-токеном і відокремити його від публічного map key.
- Додати спільний типізований парсер статусу й єдині типи помилок.
- Виправити дозвільний/геолокаційний flow та очікування background async-викликів.

### Етап 2 — архітектурні межі та стан

- Додати composition root/providers та ін’єкцію клієнта/сховищ.
- Розділити Cubit від persistence, геолокації та background orchestration.
- Включити в immutable state всі значення, що впливають на відображення.
- Винести правила домену в окремі малі тестовані компоненти без надмірної кількості шарів.

### Етап 3 — тести та автоматичні перевірки

- Замінити невалідний counter test реальними тестами продукту.
- Додати CI для форматування, аналізатора, тестів і релевантних платформних збірок.
- Перевірити тести для помилок API, відсутнього ключа, offline/cache, permission denied і background registration failure.

### Етап 4 — UI/UX, локалізація та release readiness

- Зробити дати locale-aware, додати доступні семантики/лейбли та перевірити великі шрифти.
- Перевірити продуктивність списку й карти на реальних/великих даних.
- Підготувати production application ID, release signing та документацію для кожної підтримуваної платформи.
- Виправити опис у README відповідно до справжньої функціональності.
